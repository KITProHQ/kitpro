# KITPro Host Administration capability contract v1

Status: Proposed cross-repository contract. The alpha.15 Server read-only capabilities, controlled service-management extension, disabled-by-default transient and persistent mount extensions, and disabled-by-default transactional network extension are implemented; KITPro Linux package advertisement is not implemented.

## Discovery

KITPro Server reads package-owned `/usr/lib/kitpro-linux/release.json` for the KITPro Linux ID and release. Development metadata may carry a nonempty `generation` there. Production 1.0 metadata instead declares `generation_policy: current`; the verified installed generation is recorded in `/etc/kitpro-linux-release.json`. For that policy, Server accepts the installed generation only when both files agree on `id: kitpro-linux` and `release`, and the generation is nonempty and bounded. A missing or mismatched installed record reports `unavailable`; a missing package-owned record reports `not_configured`. These records remain advisory and never authorize a privileged action. KITPro Linux package metadata and installed-generation metadata remain separate identities. A future OS release identity must be established by the Linux release process before an integration package changes it.

A future optional `host_administration` object in package-owned metadata will use `schema: 1` and name capability identifiers, required package versions, systemd unit names, helper socket contract, and upgrade/recovery prerequisites. Unknown schema versions are ignored. The installed declaration is advisory: Server probes each runtime facility and its permissions on every host. A missing declaration does not disable generic kernel read-only inspection, and a declaration never authorizes a privileged action.

## Capability values

Each capability reports `available`, `unavailable`, `unsupported`, `not_configured`, `permission_denied`, or `failed`, plus a bounded explanation. The APIs report kernel/OS facts, CPU, memory, root filesystem capacity, network interfaces, systemd runtime detection, security enforcement detection, Linux package identity, services, explicitly gated journal queries, storage inventory, read-only network inventory with controlled diagnostics and transactional configuration, and a bounded current System Health evaluation. Storage inventory includes bounded block devices, mounts, filesystem capacity, protected-resource indicators, optional LVM/ZFS visibility, and disabled-by-default transient and persistent mount operations. Network inventory includes bounded links, addresses, routes, resolver state, backend observations, counters, sampled rates, and policy-restricted diagnostics. Health distinguishes `healthy`, `warning`, `critical`, `degraded`, `unavailable`, `unsupported`, and `not_configured`, and the unified Dashboard reuses the same cached snapshot. A configured optional persistent mount that is absent reports a storage warning without asserting a critical platform failure; incomplete KITPro publication reports degraded and requires explicit recovery. The typed `ManageSystemService` extension requires `host.services.manage`, an exact principal unit/action scope or `host.security.admin`, an exact action-scoped operator catalog, canonical identity and alias protection, trusted root-owned unit definitions, bounded dependency consequence analysis, API and helper authorization, explicit confirmation, durable operation and unit-audit evidence, bounded D-Bus execution, and resulting-state verification. The typed `ManageStorageMount` extension requires `host.storage.manage`, an exact root-owned resource policy, stable UUID identity for block filesystems, canonical targets, controlled filesystem types and flags, protected-resource and mount-relationship checks, exact confirmation, independent helper revalidation, per-resource serialization, durable audit evidence, and resulting kernel-state verification. Persistence is limited to atomic KITPro-managed systemd mount units and exact wants links; `/etc/fstab`, arbitrary unit content, forced unmount, and lazy unmount remain unavailable. The typed `ManageNetworkConfiguration` extension requires `host.network.manage`, an exact root-owned interface policy, one supported owning backend, typed DHCP/static IPv4 and resolver inputs, protection of management/default-route/container/ambiguous interfaces, exact confirmation, independent helper revalidation, a durable recovery record, an independently armed rollback timer, and observed-state verification. Alpha.15 mutation is limited to exact KITPro-managed systemd-networkd profiles; NetworkManager, Netplan, primary management interfaces, arbitrary routes, IPv6 mutation, bridges, bonds, VLANs, VPNs, firewall rules, Docker networking, and raw configuration uploads remain unavailable. Permission changes revoke active sessions. Read-only previews never authorize dispatch; the helper revalidates fresh metadata. Unit and storage history require `host.audit.read`, are exact-resource and bounded, and cannot enumerate unrelated activity. Journal access independently requires `host.logs.read`, the feature gate, and OS permission. The helper provides no generic D-Bus or command interface. A failed required collector omits its value and reports `unavailable`; an optional structured provider can report malformed output as `failed`; a missing KITPro Linux package reports `not_configured`.

## Packaging and lifecycle

KITPro Server remains a separate package on Debian, Ubuntu, Arch, and experimental Rocky. KITPro Linux integration uses its separately versioned operating-system and installer release process. Packaging must preserve API/helper ownership, MAC confinement, service dependencies, and existing upgrade ordering. Service, storage, and network helper operations use the existing versioned typed protocol and independent helper policy. No other privileged method is implied by this contract.

## Recovery and compatibility

Read-only inspection adds no backup state. Future settings may be included in the existing KITPro backup format only with an explicit schema and restore policy. Machine-specific mount and network identities are never replayed across hosts without revalidation. Unsupported contract versions, absent facilities, or incompatible package versions leave mutation capabilities disabled. Upgrade qualification must include same-host recovery, older Server against newer OS metadata, newer Server against older OS metadata, and a plain Ubuntu installation with no KITPro Linux package.

## Qualification gates

Before publishing a Linux integration package, validate exact source and installed generation metadata, package ownership, service unit dependencies, permissions for each collector, AppArmor/SELinux behavior, and Installer 1.1 RC1 boot/install regression. Mutations additionally require audited helper authorization, dependency protection, rollback, and disposable-VM failure tests. No production or public release is authorized by this contract.
